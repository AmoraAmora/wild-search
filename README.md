# WB Media Downloader

Скачивание фотографий (одним zip-архивом) и видео (в MP4) из карточки товара Wildberries по артикулу или ссылке.

**🔗 Стенд: https://wild-search.vercel.app/**

На главной есть кнопки-примеры: товар с видео, товар без видео и т.д. Проверить все сценарии можно в один клик.

## Что умеет

- Поле ввода принимает **артикул или ссылку** на товар (`https://www.wildberries.ru/catalog/592995535/detail.aspx`).
- Модальное окно показывает **все фотографии** карточки. Каждую можно выбрать, по умолчанию выбраны все. Есть «Выбрать все» и счётчик «Выбрано N из M».
- **«Скачать фото»** — zip только с выбранными фото, в **лучшем доступном качестве**.
- **«Скачать видео»** — видео в **максимальном доступном качестве в MP4**. На кнопке видно качество и длительность, например «1440p · 0:26». Если у товара нет видео, кнопка неактивна с подсказкой.
- Прогресс скачивания на кнопке. Закрытие окна отменяет скачивание.
- Понятные состояния: загрузка (скелетоны), «товар не найден», нет сети или WB недоступен (с кнопкой «Повторить»).
- Адаптивная вёрстка: на телефоне модалка во весь экран.

## Какой подход к получению медиа выбран и почему

### Карточка: публичный CDN вместо `__internal/.../detail`

Предложенный в задании `wildberries.ru/__internal/card/cards/v4/detail` закрыт антиботом WB: без браузерных cookie он отвечает **403**. Для работы через него нужен бэкенд-прокси с обходом защиты, а это хрупко и не нужно.

Все нужные данные отдаёт **CDN-корзина товара**, и у неё `Access-Control-Allow-Origin: *`, поэтому всё работает **прямо из браузера, без своего бэкенда**:

```
1. GET https://cdn.wbbasket.ru/api/v3/upstreams          → карта хостов (какая корзина обслуживает какой vol)
2. GET https://basket-XX.wbbasket.ru/vol{nm/1e5}/part{nm/1e3}/{nm}/info/ru/card.json
       → название, бренд, media.photo_count, media.has_video, media.best_qualities_photos
```

Формулы URL взяты из gist в задании и переписаны чистыми функциями с тестами на реальных значениях ([`shared/api/wb-cdn`](src/shared/api/wb-cdn)). Ответы WB проверяются zod-схемами только по нужным полям. Если WB поменяет формат, это будет явная ошибка, а не тихо собранные битые ссылки.

### Фото: лучшее качество без лишних запросов

Размеры фото: `c246x328` (превью для сетки), `big`, `hq` (оригинал). Но `hq` есть не у всех фото. Проверкой на реальных карточках я выяснила, что **`hq` существует ровно у фото из `media.best_qualities_photos`**, у остальных CDN отдаёт 404. Поэтому качество для скачивания выбирается заранее (`hq` или `big`), без пробных запросов.

Скачивание идёт с ограничением параллельности (6 запросов), с прогрессом и отменой. Zip собирается через fflate **без сжатия** (`level: 0`): webp уже сжат, так что архив того же размера, а сборка сводится к копированию памяти. Если хотя бы одно фото не скачалось, неполный архив не создаётся.

### Видео: HLS → обычный MP4 прямо в браузере

WB хранит видео как **HLS**: плейлист `…/hls/{1440p|1080p|720p}/index.m3u8` и сегменты MPEG-TS (H.264 + AAC). Готового MP4 нет. Решение:

1. **Качество.** Набор качеств у каждого товара свой (часто есть только `1440p`). Все варианты проверяются параллельно, выбирается лучший из существующих. Если все 404 — видео нет. Если CDN отвечает ошибкой — это явная ошибка, а не «нет видео».
2. **Сегменты** скачиваются параллельно с сохранением порядка и склеиваются: MPEG-TS можно просто конкатенировать.
3. **Перепаковка в MP4 без перекодирования** через mediabunny: 80–400 мс на ролик, качество не теряется.

**Почему mediabunny, а не mux.js.** Первым прототипом был mux.js, и он **не подошёл**. Он собирает _фрагментированный_ MP4 для стриминга и пишет в заголовок длительность `0xFFFFFFFF`. QuickTime показывал такой файл как **27-часовой**, а AVFoundation не мог извлечь из него ни одного кадра. Исправление длительности в заголовке не помогло: системный плеер читал только первый фрагмент. mediabunny собирает **обычный** MP4 с `moov` в начале файла. Результат проверен через AVFoundation (длительность 11,57 с и 26,10 с, кадры с конца ролика извлекаются) и в QuickTime.

### Серверный стейт (TanStack Query)

| Запрос           | Ключ                         | Политика                                                                                                  |
| ---------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------- |
| Карта хостов CDN | `['wb-cdn','routes']`        | `staleTime: Infinity`: один запрос на сессию. Запрос карточки получает её через `client.ensureQueryData`  |
| Карточка товара  | `['product', nmId, 'media']` | `staleTime` 5 мин, повтор только при временных ошибках                                                    |
| Источник видео   | `['video-source', baseUrl]`  | `skipToken`, если у товара нет видео                                                                      |
| Скачивания       | мутации (`useFileDownload`)  | прогресс в целых процентах, отмена через `AbortController` при закрытии окна, отмена не считается ошибкой |

- **Повторы.** По умолчанию Query повторяет запрос 3 раза при **любой** ошибке. Здесь повторяются только сетевые сбои и ответы 5xx, 408, 429: 404, «товар не найден» или изменение формата ответа повтор не исправит.
- **Ошибки.** Неожиданные ошибки (баги, изменение формата ответа WB) собираются в одном месте через `QueryCache`/`MutationCache.onError` и ErrorBoundary. Здесь в продакшене подключается Sentry.

### Архитектура (FSD)

```
src/
  app/        провайдеры (Query, тема), ErrorBoundary, отчёт об ошибках, перезагрузка при устаревших чанках
  pages/      home (форма + ленивая модалка), crash (экран сбоя)
  widgets/    media-download-modal — собирает фичи в модальное окно
  features/   select-photos, download-photos, download-video — независимы друг от друга
  entities/   product — card.json → доменная модель ProductMedia, разбор артикула/ссылки
  shared/     api (http, wb-cdn, retry-policy), lib (параллельность, хук скачивания), ui, config
```

Фичи не зависят от модалки: кнопку «Скачать видео» можно поставить, например, на страницу товара без изменений. Правило steiger `insignificant-slice` осознанно отключено (обоснование в [`steiger.config.ts`](steiger.config.ts)). В одностраничном приложении у любого слайса ровно один потребитель, и правило требовало бы свернуть всё в `pages/home`.

### Производительность

|                                                                         | gzip                                    |
| ----------------------------------------------------------------------- | --------------------------------------- |
| Начальная загрузка (React + MUI + приложение)                           | **149 КБ** (было 202 КБ до оптимизаций) |
| Модалка: грузится лениво и **предзагружается при фокусе на поле ввода** | 37 КБ                                   |
| mediabunny: только при нажатии «Скачать видео»                          | 90 КБ                                   |
| fflate: только при сборке zip                                           | 4 КБ                                    |

- **Как получены 149 КБ:** `zod` заменён на `zod/mini` (tree-shaking), тяжёлые библиотеки и модалка вынесены в ленивые чанки, а `"sideEffects": false` позволяет выбросить неиспользуемые реэкспорты из barrel-файлов (иначе в основной бандл попадали zod-схемы).
- **Сетка:** превью `c246x328` с `loading="lazy"`, плитки в `memo` со стабильными колбэками, поэтому клик по одному фото не перерисовывает остальные.
- **После деплоя** открытая вкладка ссылается на старые хеши чанков. По событию `vite:preloadError` страница один раз перезагружается, с защитой от цикла.

## Самопроверка: что нашла и исправила

Код писался с ИИ-ассистентом. Ниже — что я нашла при ревью и как исправила.

- **mux.js давал «битый» MP4** (длительность 27 ч в QuickTime) — заменён на mediabunny, см. выше.
- **`instanceof TypeError` как признак «нет сети»** выдавал бы баги в коде за проблемы сети. Введён собственный `NetworkError`, в который оборачивается только сбой `fetch`.
- **Повторы на любую ошибку** (дефолт Query): заменены политикой «только временные ошибки».
- **Бандл вырос до 202 КБ.** Разобран по пакетам через source map: `zod/mini`, ленивые чанки и `sideEffects: false` дали 149 КБ. Дважды при этом ловила регрессии: импорт доменной ошибки в слой `app` и barrel-реэкспорты тянули zod в основной бандл. Решено базовым `ExpectedError` в `shared`.
- **Раздутый публичный API.** 9 экспортов слайсов никто снаружи не использовал, API сужен.
- **Распарсенная, но неиспользуемая длительность видео** — выведена на кнопку.
- **Хук скачивания без тестов** — покрыт. Проверила, что тест действительно падает, если убрать проверку отмены (иначе файл скачивался бы после закрытия окна).
- **Вёрстка.** Закреплённая панель была сдвинута на 24px: отступы `Stack` через `margin` перебивали её отрицательный `margin`. Найдено измерением в браузере, исправлено `useFlexGap`.

Итог: нет `any`, приведений `as` (кроме `as const`), non-null `!`, `eslint-disable` и `@ts-ignore`. Единственный `useEffect` — отмена скачивания при размонтировании.

**Проверено на стенде** (https://wild-search.vercel.app/) автоматическим сценарием в Chrome: ввод артикула и ссылки, неверный ввод, выбор фото, zip (19 из 21 фото), MP4 (26,10 с, проигрывается), товар без видео, несуществующий артикул, одна загрузка карты хостов на всю сессию.

## Что бы доделала для продакшена

### Видео

- **Перепаковку — на сервер или в Web Worker.** Сейчас MP4 собирается в основном потоке. Для роликов WB (10–30 с, до ~10 МБ) это 80–400 мс, но длинное видео заморозит интерфейс. Варианты: Worker с тем же mediabunny или серверная функция с `ffmpeg -c copy` и кешированием готовых MP4 по `nmId + quality`.
- **Потоковая запись на диск.** Сейчас видео целиком держится в памяти примерно в трёх копиях (сегменты → склейка → MP4). Для больших файлов: File System Access API / StreamSaver, чтобы писать по мере скачивания.
- **Повтор отдельных сегментов** с backoff, а не провал всей загрузки из-за одного сегмента.
- **Выбор качества пользователем** и честное разрешение в подписи. Папка `1440p` не гарантирует 1440p: у товара 592995535 там лежит видео **480×640**. Разрешение надо брать из самого потока (mediabunny его отдаёт) и показывать на кнопке.
- **Мониторинг формата HLS.** Сейчас мастер-плейлисты, шифрование и fMP4-сегменты явно отклоняются с понятной ошибкой. Если WB начнёт их использовать, это должен заметить мониторинг, а не пользователь.

### Остальное

- **CI** (GitHub Actions: typecheck, lint, unit, build) и **E2E на Playwright** с замоканными ответами WB. Сценарий, которым проверялся стенд, стоит перенести в репозиторий.
- **Sentry** в `reportError` — в первую очередь ради ошибок валидации схем, то есть изменений непубличного API.
- **Тесты UI-компонентов** (сейчас покрыты логика и хуки).
- **Бэкенд-прокси** как запасной вариант на случай, если WB закроет CORS на CDN.

## Ограничения, с которыми столкнулась

- **Непубличный API.** Формулы шардирования, формат `card.json`, пути HLS — всё это может поменяться без предупреждения. Схемы и явные ошибки сделают поломку заметной, но не предотвратят её.
- **Эндпоинт из задания закрыт антиботом** (403), поэтому используется CDN.
- **Доступность WB зависит от сети пользователя.** С включённым VPN адреса WB не открывались вовсе: `ERR_ADDRESS_INVALID` в браузере, `Can't assign requested address` в curl. Приложение показывает «Нет доступа к серверам Wildberries… отключите VPN», но работать без собственного бэкенда-прокси в такой сети оно не может.
- **Набор качеств видео разный у разных товаров,** а название папки не соответствует реальному разрешению (см. выше).
- **Две ошибки 404 в консоли** при открытии товара — это проверка качеств 1080p/720p, которых у товара нет. Браузер всегда логирует неудачные загрузки, подавить это из кода нельзя.
- **Видео целиком в памяти** — приемлемо для роликов WB, но не масштабируется на длинные видео.
- **Автоматически проверено только в Chrome** (включая продакшен-стенд). В Safari и Firefox автоматических проверок не было.
